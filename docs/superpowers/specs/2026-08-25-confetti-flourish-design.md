# 색종이 화려화 설계

> 상태: 승인됨 · 2026-08-25
> 개정 대상: [파티 포퍼 기믹 설계](2026-08-24-popper-gimmick-design.md) §7

---

## 0. 무엇을 바꾸는가

색종이가 **전부 같은 흰 직사각형 하나**를 팔레트 6색으로 틴트한 것이라, 한
발에 120개가 날아도 "같은 조각의 반복"으로 읽힌다. 두 가지를 더해 화려하게
만든다.

1. **모양 4종** — 직사각·리본·원형·마름모. 전부 "잘린 종이"로 읽히는
   구성이라 포퍼의 문법을 깨지 않는다.
2. **개체 1/3의 금박 반짝임** — 회전하며 빛을 스치는 조각이 섞인다.

**팔레트 6색, 발사당 개수(`40 + 80 × power`), 물리 상수, 풀 크기 256,
드로우콜 1번은 전부 그대로다.** 원 스펙 §7이
"펜의 전면 랜덤 RGB는 탁한 색이 절반이라 버린다 — 고정 팔레트가 깔끔하게의
일부"라고 정한 결정을 뒤집지 않는다. 화려함은 색 수가 아니라 모양과 빛에서
낸다.

## 1. 스프라이트 아틀라스 — 종이 4종

### 셀을 정사각으로 통일하는 이유

RSXform은 스프라이트의 (0,0)을 기준으로 변환하므로, 회전이 조각 중심을
축으로 돌게 하려면 평행이동에서 중심 오프셋을 빼줘야 한다(현재 코드의
`cx = SPRITE_W / 2`, `cy = SPRITE_H / 2`). 모양마다 소스 사각형 크기가
다르면 이 보정값이 개체마다 갈라져 워크릿에 분기와 조회가 들어온다.

**셀 12×12로 통일하고 각 모양을 셀 중앙에 그린다.** 보정값이
`CELL / 2`(=6) 하나로 남는다. 텍스처는 가로로 이어붙인 48×12 한 장이다.

| 칸 | 모양 | 치수 | 셀 내 배치 |
|---|---|---|---|
| 0 | 직사각 | 6×10 | `Rect x=3 y=1 w=6 h=10` |
| 1 | 리본 | 3×11 | `Rect x=4.5 y=0.5 w=3 h=11` |
| 2 | 원형 | r 4.5 | `Circle cx=6 cy=6 r=4.5` |
| 3 | 마름모 | 8×8 | `Path (6,2)→(10,6)→(6,10)→(2,6)` |

직사각 칸은 지금 조각과 같은 6×10이다 — 기존 손맛의 기준점을 남긴다.

**모든 모양은 셀 경계에서 최소 0.5pt 안쪽에 둔다.** 칸이 가로로 붙어 있어
텍스처를 겹선형 필터링으로 샘플링하면 경계에 닿은 픽셀이 이웃 칸의 색을
빨아들인다. 리본을 3×12가 아니라 3×11로 잡은 게 이 이유다.

`TEXTURE_SIZE`는 **반드시 모듈 상수**다. 현재 `SPRITE_SIZE`에 달린 주석과
같은 이유로, `usePictureAsTexture`의 deps에 그대로 들어가므로 인라인
리터럴이면 발사마다 텍스처를 새로 굽는다.

### 모양은 파티클이 아니라 풀 슬롯에 붙는다

Skia `Atlas`에서 애니메이션 버퍼는 `transforms`(`useRSXformBuffer`)와
`colors`(`useColorBuffer`) 둘뿐이다. **`sprites`는 정적 배열이라 워크릿에서
바꿀 수 없다.** 그래서 모양을 스폰 시점에 개체별로 뽑는 건 불가능하다.

대신 슬롯 `i`가 `i % 4`번 칸을 영구히 가리키게 한다.

```
SPRITES[i] = XYWHRect((i % SHAPE_COUNT) * CELL, 0, CELL, CELL)
```

스폰이 링버퍼를 순차로 훑으므로 한 발(최소 40개)이면 네 모양이 자동으로
균등하게 섞인다. 분기도 랜덤 호출도 런타임 비용도 없다.

**`POOL_SIZE`는 `SHAPE_COUNT`로 나누어떨어져야 한다.** 256 % 4 == 0이라
링 랩어라운드에서도 정렬이 유지된다. 이 조건은 코드 주석으로 못 박는다 —
나중에 풀 크기를 250 같은 값으로 바꾸면 특정 모양이 조용히 더 자주 나온다.

## 2. 금박 반짝임 — 개체의 1/3

`Particle`에 `foil: 0 | 1` 한 필드를 더하고 스폰에서 정한다.

```
particle.foil = Math.random() < FOIL_RATIO ? 1 : 0   // FOIL_RATIO = 0.34
```

**물리 루프는 손대지 않는다.** 반짝임은 색 버퍼 안에서만 일어난다 —
위치·속도·수명 어디에도 영향이 없다.

### 위상은 이미 있는 flutter를 재사용한다

변환 버퍼가 쓰는 `flutter = 0.75 + 0.25 × sin(rot × 3)`이 최대일 때가 조각이
정면으로 가장 넓게 보이는 순간이다. 빛을 반사할 순간과 물리적으로 같은
위상이므로 **같은 `sin(rot × 3)`을 색에도 쓴다.** 새 상태를 만들지 않는다.

`s = sin(rot × 3)`이라 할 때, 금박 조각만:

- **번쩍** (`s > 0`) — `s⁴`에 비례해 따뜻한 흰색 `SHEEN = (1.0, 0.97, 0.86)`
  쪽으로 보간한다.

  ```
  k = GLINT_STRENGTH × s⁴          // GLINT_STRENGTH = 0.65
  c = c + (SHEEN − c) × k          // 채널별
  ```

  4제곱이라 부드럽게 부푸는 대신 날카롭게 스친다. "빛나는 색"이 아니라
  "빛을 스치는 종이"로 읽히는 지점이다. 순수 흰색이 아니라 살짝 노란
  흰색인 이유는 형광이 아니라 금박으로 읽히게 하려는 것이다.

- **뒷면** (`s < 0`) — `s²`에 비례해 어둡게 한다.

  ```
  c = c × (1 − SHADE_STRENGTH × s²)   // SHADE_STRENGTH = 0.25
  ```

  이 대비가 있어야 깜빡임이 아니라 **회전으로** 읽힌다.

두 갈래는 `s`의 부호로 갈리므로 동시에 적용되지 않는다. 결과는 항상
0~1이다 — `SHEEN` 쪽 보간은 두 끝점이 모두 0~1이고, 뒷면은 0~1 계수를
곱하기만 한다.

무광 조각(2/3)은 현재 코드 그대로 팔레트 색만 쓴다.

수명 끝 페이드아웃(`color[3]`)은 건드리지 않는다.

### 왜 전량이 아니라 1/3인가

전부 반짝이면 균질해져서 종이가 아니라 플라스틱으로 읽힌다. 무광이 섞여
있어야 번쩍이는 조각이 도드라진다 — 대비가 화려함을 만든다.

## 3. 범위 밖

- **팔레트 확장** — 원 스펙 §7의 고정 6색 결정을 유지한다.
- **물량·크기 증가** — 풀 256 상한이라 연사 시 재활용이 눈에 띌 수 있다.
- **접힘 음영** — 텍스처에 명암을 구워 조각마다 접힌 느낌을 내는 것.
  블렌드가 `modulate`로 바뀌었으니(§6) 이제 텍스처 내부 명암이 살아남아
  공짜에 가깝지만, 이번 요청의 범위가 아니다. 실기기에서 더 필요하면 후속.
- **모양별 물리 차이** — 리본이 더 팔랑거린다든가. 모양이 슬롯에 묶여
  있어 물리에서 모양을 알려면 조회가 하나 더 붙는다. 값어치가 확인되기
  전에는 안 한다.

## 4. 검증의 한계

**발사는 터치 제스처라 시뮬레이터에서 트리거할 수 없다.** 딥링크로 포퍼
화면까지는 가지만, 당겨서 놓는 입력은 넣을 수 없다.

다만 구현 중에 우회로를 찾았다 — **임시 자동 발사를 잠깐 주입했다 되돌리면**
시뮬레이터에서 실제 발사를 볼 수 있다. §6의 블렌드 버그를 잡은 게 이
방법이다. 스크린샷은 순수 파이썬 PNG 디코더로 픽셀을 직접 세어 판정했다 —
눈대중으로는 "흰 조각도 색종이처럼 보인다"에 속는다.

그래도 **손맛과 강도는 실기기에서 손으로 쏴 봐야 한다.**

자동으로 확인 가능한 것은 여기까지다:

1. **타입 체크** — `tsc`.
2. **glint 수식의 치역** — `s`를 전 구간 스윕해 결과 RGB가 0~1을 벗어나지
   않음을 Node로 확인.
3. **슬롯↔모양 배정** — `i % 4` 분포와 랩어라운드 정렬을 Node로 확인.

2·3이 가능하려면 그 수학이 **import 없는 파일**에 있어야 한다. Node의 타입
스트리핑은 타입만 벗겨낼 뿐이라, Skia나 Reanimated를 부르는 모듈은 실행되지
않는다. 그래서 겉모습 수학을 `confettiLook.ts`로 떼어낸다 — `bulb/cordPhysics.ts`가
같은 이유로 `bulb/cord.ts`에서 분리돼 있는 것과 같은 구조다.

분리에는 검증 말고 또 하나의 이유가 있다. 플러터 위상 `sin(rot × 3)`이 지금
변환 버퍼 안에 인라인으로 박혀 있는데, §2의 번쩍임이 **같은 위상**을 써야
한다. 두 곳에 각각 두면 한쪽만 고쳤을 때 조용히 어긋난다 — 상수
`FLUTTER_CYCLES` 하나를 두 곳이 공유하게 만든다.

원 스펙 §7의 물리 상수가 지금도 "실기기 미검증"으로 남아 있는 것과 같은
상태다. 수치(`FOIL_RATIO` 0.34, `GLINT_STRENGTH` 0.65, 마름모 8×8 등)는
실기기에서 손맛 보고 조정할 값으로 둔다.

## 6. 구현 중 발견: 색이 아예 안 먹고 있었다

**설계 시점에는 몰랐던 기존 버그다.** 이 변경을 붙이고 실기기에서 처음
발사시켜 보니 조각이 순백으로 나왔다. 이번 변경 탓인지 확인하려고 변경 전
코드로 되돌려 다시 찍었더니 **똑같이 흰색이었다** — 시뮬레이터 스크린샷의
픽셀을 세어 보니 밝은 픽셀의 99%가 무채색이었다. 팔레트 6색이 실기기에서
한 번도 먹은 적이 없다.

눈치채지 못한 이유는 분명하다. 기존 스프라이트는 텍스처를 꽉 채우는 단색
사각형이라, 색이 안 먹어도 "흰 조각이 날아가는" 그림이 그럴듯했다. 원 스펙
§7의 팔레트는 코드에만 있었고 화면에는 없었다.

원인은 Skia `drawAtlas`에서 색과 텍셀 중 **어느 쪽이 소스인지**가 이 조합에서
뒤집히는 것으로 보인다. 그러면 `srcIn`이 `텍셀 × 색알파`로 계산되어 흰 텍셀이
그대로 나온다 — 관측과 정확히 맞는다.

**`modulate`로 바꾼다.** `src × dst`라서 **피연산자 순서와 무관하게** 같은
결과를 낸다 — 위 불확실성에 영향받지 않는다는 게 이 선택의 핵심이다. 흰
텍셀은 개체색을 그대로 통과시키고, 안티앨리어싱 가장자리(프리멀티플라이드
부분 알파)도 올바르게 감쇠한다. 수정 후 무채색 비율은 99% → 18%로 떨어졌고
(남은 18%는 상단 카운터 알약과 금박 번쩍임), 상위 색이 전부 팔레트다.

원 스펙 §7의 `srcIn` 결정을 뒤집는 변경이지만, 선호가 아니라 **증거**가
뒤집었다.
