# 갤러리 타일 그리드 설계

> 상태: 승인됨 · 2026-08-25
> 변경 범위: 앱 셸만. 기믹 핫패스(`src/gimmicks/*/index.tsx`)는 한 줄도 건드리지 않는다.

---

## 0. 무엇을 바꾸는가

홈 갤러리가 **세로 목록 + 셰브론**이다. 항목마다 이름·입력모델·횟수를 두 줄로
쓰고 오른쪽에 `>` 를 붙이는 구조라, 네 개뿐인 장난감이 설정 메뉴처럼 읽힌다.
피젯 토이 컬렉션 앱의 첫 화면이 설정 화면처럼 보이는 게 문제다.

두 축으로 바꾼다.

1. **심플** — 셰브론 4개, 입력모델 전용 줄, 카드 테두리·그림자를 없앤다.
   네이티브 헤더도 끈다.
2. **재미** — 2열 정사각 타일, 기믹별 아이콘, 기믹별 틴트, 눌림 반응.

그리고 앱 이름을 **'토이앱'**으로 확정한다(기존 표시 문구는 '만지작'이었다).

### 제약: 살아있는 미리보기는 불가능하다

"재미"를 내는 가장 강력한 수단은 타일 안에서 실제 기믹이 조금씩 움직이는
것이다. **§4 원칙 2가 이를 금지한다** — 갤러리 카드는 기믹 컴포넌트를
import하지 않는다. import하면 lazy가 무의미해지고 초기 번들에 Skia 씬이
딸려온다. 기믹 30개를 목표로 하는 구조에서 이 원칙이 먼저다.

따라서 재미는 **셸이 가진 것만으로** 낸다: 아이콘, 색, 크기, 여백, 눌림 모션.

## 1. 레이아웃

```
토이앱                          ☾
손이 심심할 때

┌───────────┐ ┌───────────┐
│  ⌨        │ │  ◎        │
│           │ │           │
│ 키캡      │ │ 다이얼    │
│ 156회     │ │ 51회      │
└───────────┘ └───────────┘
┌───────────┐ ┌───────────┐
│  ☀        │ │  ✦        │
│           │ │           │
│ 전구      │ │ 파티 포퍼 │
│ 106회     │ │ 159회     │
└───────────┘ └───────────┘
```

- 타일: `aspect-square`, `rounded-2xl`, 2열 `gap-3`
- 아이콘은 위쪽, 텍스트는 아래쪽. 사이는 `flex-1`이 밀어낸다.
- 컨테이너는 `flex-row flex-wrap` + 각 타일 `w-[48%]`.

### 왜 FlashList가 아닌가

§2가 "캐러셀 라이브러리는 쓰지 않는다 — RNR 카드 + FlashList로 충분"이라고
정했고, 기존 코드 주석도 "목록이 길어지면 FlashList로 바꾼다"고 예고해 뒀다.
기믹 4개에서는 여전히 `ScrollView`가 맞다. 다만 **2열이 되면서 전환 시점이
멀어졌다** — 한 화면에 8개가 들어가므로 같은 스크롤 길이가 기믹 두 배를
담는다. 주석의 개수(2개)를 현재 값으로 고치고 전환 조건은 그대로 남긴다.

### 카운트가 0일 때 입력모델을 대신 보여준다

타일은 높이가 고정이라 아래 한 줄이 비면 레이아웃이 뜬다. 기존 목록에서는
`count > 0`일 때만 `· 156회`를 덧붙였는데, 타일에서는 그 줄이 사라지면 안 된다.

```
count > 0  →  "156회"
count = 0  →  "누르기"      (KIND_LABELS)
```

정보를 잃지 않으면서, 아직 안 만져본 장난감에는 횟수보다 쓸모 있는 것("어떻게
만지는 물건인가")이 온다. 한 번 만지면 그 자리가 횟수로 바뀌므로 **입력모델
라벨은 첫 조작까지만 쓰이는 힌트**가 된다. `KIND_LABELS`는 그대로 유지한다.

## 2. 네이티브 헤더를 끈다

기믹 화면은 이미 `headerShown: false`다(기믹이 상태바 아래까지 배경을
소유해야 하므로). 홈만 네이티브 헤더를 써서 구분선과 중앙 정렬 제목이 있는데,
이건 심플과 반대 방향이다.

`headerShown: false`로 두고 화면 안에 직접 그린다.

- 제목 `토이앱` — 왼쪽 정렬, `text-3xl font-bold`
- 부제 `손이 심심할 때` — §0이 정한 톤이다. "불안 감소" 류 문구 금지 규칙을
  지키는 자리이므로 지운다는 선택지는 없었고, 제목 아래로 붙여 한 덩어리로
  만든다.
- 오른쪽에 테마 토글. 동작은 지금과 같다(`Uniwind.setTheme`).

**상단 인셋을 직접 넣어야 한다.** 헤더가 사라지면 상태바 아래 여백을 아무도
주지 않는다. `useSafeAreaInsets().top`을 `ScrollView`의
`contentContainerStyle.paddingTop`에 더한다 — `[id].tsx`가 오버레이에서 쓰는
것과 같은 방법이다.

## 3. 색 — 기믹의 시그니처를 타일이 물려받는다

각 기믹 씬에 **이미 존재하는 색**에서 따온다. 임의 배색이 아니라, 타일을 눌러
들어가면 같은 색이 화면을 채운다. 갤러리와 기믹 사이에 시각적 연속성이 생기고,
새 기믹의 틴트를 정하는 규칙("그 기믹의 지배색")도 함께 정해진다.

| 기믹 | 틴트 | 출처 |
|---|---|---|
| 키캡 | `blue` | 배경 그라디언트 `#1a5ce0` |
| 다이얼 | `emerald` | 혜성 팔레트 첫 색 `#1DD1A1` |
| 전구 | `amber` | 글로우 `#ffd97a` |
| 파티 포퍼 | `rose` | 콘 베이스 `#ff6b6b` |

네 색이 색상환에서 충분히 떨어져 있어 4개가 한 화면에 있어도 서로 안 먹는다.

### 테마 토큰으로 올리지 않는다

[`theme.ts`](../../../src/lib/theme.ts)와
[`global.css`](../../../src/global.css)의 무채색 토큰은 **건드리지 않는다.**
틴트는 갤러리 타일 전용이고, 셸의 나머지(버튼·시트·설정)는 계속 무채색이다.
지금 `--color-tint-*` 를 만들면 셸 전체가 쓸 수 있는 색이라고 선언하는 것이
되는데, 그건 결정한 바가 없다.

대신 Tailwind 기본 팔레트를 쓴다. `@import "tailwindcss"`가 이미 들어와 있어
`blue-500` 같은 색이 그대로 잡힌다.

`src/lib/tints.ts`:

```
TINTS = {
  blue:    { surface: 'bg-blue-500/10 dark:bg-blue-500/15 border-blue-500/20',
             icon: 'text-blue-600 dark:text-blue-400' },
  emerald: ...
  amber:   ...
  rose:    ...
}
```

**클래스 문자열을 리터럴로 적어두는 게 핵심이다.** Tailwind는 소스를 스캔해서
쓰인 클래스만 만든다. `bg-${tint}-500/10` 처럼 조립하면 스캐너가 못 보고
런타임에 색이 안 나온다. 4개를 전부 적어두는 게 이 제약에 대한 값이다.

배경을 `/10`(다크 `/15`)로 낮게 잡은 이유: 타일 위에 `foreground` 색 텍스트가
올라간다. 채도가 높으면 라이트 모드에서 검정 글씨가, 다크 모드에서 흰 글씨가
읽히지 않는다. 색은 "어느 장난감인지 알아보는 신호"까지만 하고 가독성은
기존 토큰에 맡긴다.

## 4. 아이콘 — registry에 `look` 필드를 추가한다

lucide에서 정확히 대응하는 것이 네 개 다 있다(존재 확인함).

| 기믹 | 아이콘 |
|---|---|
| 키캡 | `KeyboardIcon` |
| 다이얼 | `Disc3Icon` |
| 전구 | `LightbulbIcon` |
| 파티 포퍼 | `PartyPopperIcon` |

### 어디에 두는가 — 이 설계의 유일한 논쟁거리

세 후보가 있었다.

1. **기믹 컴포넌트** — `GimmickVariant` 주석이 "시각 정보는 기믹 컴포넌트가
   자기 것으로 갖는다"고 정한 자리다. **불가능하다**: §4 원칙 2가 갤러리의
   기믹 컴포넌트 import를 금지한다. 그 원칙이 성립하는 한, 갤러리가 쓸 시각
   정보는 컴포넌트 밖에 있어야 한다.
2. **셸 소유의 별도 맵** (`src/app/galleryLook.ts` 류) — registry를 순수하게
   유지한다. 대신 **기믹 추가 비용이 2곳에서 3곳으로 늘어난다.** registry
   주석이 명시한 목표("새 기믹 = 여기 항목 하나 + 폴더 하나")를 깬다.
3. **registry의 `GimmickBase`** — 채택.

`GimmickBase`에는 이미 `name`(표시명)과 `sound?`(에셋 키)가 있다. 둘 다 셸이
읽는 표시용 데이터다. 갤러리 썸네일도 같은 성격이고, §4 원칙 2가 이걸 registry
밖에 둘 수 없게 만들었다.

```
look: {
  icon: LucideIcon;
  tint: TintName;
}
```

필수 필드로 둔다. 옵셔널이면 새 기믹이 아이콘 없이 갤러리에 나타날 수 있고,
그때 빈 타일이 뜨는 걸 컴파일 타임에 막을 방법이 없어진다.

### 대가: registry가 완전한 JSON이 아니게 된다

registry 주석은 "항목이 순수 데이터 + lazy 컴포넌트이므로 신규 기믹을
EAS Update로 심사 없이 배포할 수 있다"고 했다. `icon`이 컴포넌트 참조이므로
이 문장의 "순수 데이터"가 약해진다.

- **EAS Update(§7)는 영향 없다.** JS 번들을 실어 보내므로 컴포넌트 참조가
  문제되지 않는다. 주석이 근거로 든 능력은 그대로 유지된다.
- **서버 주도 registry는 영향받는다.** 지금 없는 요구사항이라 YAGNI로
  처리한다. 필요해지면 `icon`을 문자열 키로 바꾸고 셸에 아이콘 맵을 두면
  된다 — `tint`가 이미 그 형태(이름 → 클래스 맵)라 전례가 있다.

`tint`를 이름 키로 둔 이유가 여기 있다. 클래스 문자열은 셸의 관심사(테마)이고,
registry는 "이 기믹은 파란색"까지만 말한다.

## 5. 인터랙션

### 구조

```
Link asChild
  └ Pressable          ← 터치와 라우팅
      └ Animated.View  ← 스케일
          └ 내용
```

`Link asChild`는 자식을 복제해 `onPress`를 주입한다. 애니메이션 컴포넌트를
그 자리에 두면 Link의 주입과 Reanimated의 props 처리가 같은 컴포넌트에서
만난다. 스케일을 **안쪽** `Animated.View`로 내려 그 접점을 없앤다. Pressable은
평범한 Pressable로 남는다.

### 모션

- `onPressIn` → `withSpring(0.96)`
- `onPressOut` → `withSpring(1)`

§1의 "기믹 화면 내부에서 `className`을 쓰지 않는다"는 여기 적용되지 않는다.
금지 방향은 한쪽이다 — 기믹 화면에서 Tailwind를 쓰지 말라는 것이고, 셸에서
Reanimated를 쓰지 말라고는 하지 않았다. `[id].tsx`가 셸이면서 `className`을
쓰는 것과 같은 판단이다. 이 타일은 드래그 중 매 프레임 스타일이 바뀌는 구간이
아니라 누를 때 한 번 스프링이 도는 것이므로, 정적 스타일은 Tailwind가,
스케일 하나는 shared value가 담당한다.

### 햅틱

`onPressIn`에서 프리셋 한 방. **§0이 "햅틱이 곧 제품"이라고 한 앱에서 첫
화면이 무반응인 건 어색하다** — 손맛이 갤러리에서부터 시작하는 게 맞다.

JS 스레드에서 직접 부른다. Pulsar 프리셋은 내부가
`Pulsar.Pulsar_play('name')` 네이티브 호출 하나뿐이고, `'worklet'` 지시자는
UI 스레드에서도 부를 수 있게 하는 것이지 JS 스레드를 막는 게 아니다. 기믹들이
워크릿에서 부르는 건 제스처 핸들러가 UI 스레드에 있기 때문이고, 여기는
`Pressable`의 JS 콜백이므로 스레드 홉을 만들 이유가 없다.

`useThrottledHaptic`도 쓰지 않는다. 그건 드래그 중 초당 수십 회를 스로틀하는
장치다(§5의 초당 20회 드랍 한계). 타일 탭은 손가락이 한 번 닿는 것이라
스로틀할 대상이 없다.

**preload는 하지 않는다.** [`engine.ts`](../../../src/haptics/engine.ts)가
기록한 릴리스 무음 버그의 원인이 정확히 "엔진 준비 전 preload"였다. 온디맨드
로딩으로 충분하다는 것도 같은 주석이 확인해 뒀다.

프리셋은 `nudge`(가벼운 밀림)로 시작한다. **⚠️ 실기기 미검증.** registry가
같은 상황에 붙인 표시와 같은 뜻이다 — 시뮬레이터에는 햅틱이 없으므로(§5)
이 값은 실기기에서 후보를 손으로 비교해 고쳐야 한다. 후보:
`nudge`, `blip`, `pip`, `poke`, `flick`.

## 6. 앱 이름

두 곳이다.

- **화면 제목** — `'만지작'` → `'토이앱'`. §2 헤더 절로 이동한다.
- **스토어 표시명** — [`app.config.ts`](../../../app.config.ts)의
  `name: 'toy-app'` → `'토이앱'`.

`app.config.ts`의 `name`에는 §9를 참조하는 TODO가 달려 있다("주력 시장 확정 후
브랜드명으로 교체"). 이번 결정이 그 자리를 채우므로 TODO를 걷어낸다. 남길
것과 걷을 것을 구분한다.

- 걷는다: "지금은 플레이스홀더", "TODO(§9) 주력 시장 확정 후 교체"
- 남긴다: §8의 "언제든 변경 가능"과 ASO 규칙(이름에 "Fidget"을 넣지 않고
  부제에 넣는다). 부제는 아직 안 정했으므로 그 규칙은 살아있는 제약이다.
  '토이앱'은 이미 이 규칙을 만족한다.

`CODENAME`(`toyapp`)과 `BUNDLE_ID`는 **건드리지 않는다.** §8이 출시 후 변경
불가라고 못박은 값이고, 코드네임을 브랜드명과 분리해 둔 이유가 바로 이런
리브랜딩을 자유롭게 하기 위해서다. 이번 변경이 그 설계가 의도대로 동작하는
첫 사례다.
